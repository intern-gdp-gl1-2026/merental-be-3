### CRIT-002: DEBUG is enabled in settings (DEBUG = True)
- Files / lines:
  - /Users/admin/Desktop/intern/gdp/merental-be-3/merentalbe3/settings.py line 29 (DEBUG = True)
- One-sentence impact: DEBUG = True in production leaks detailed error pages and stack traces (including secrets, environment variables, local paths), enabling attackers to gain sensitive information about the system.
- Remediation (immediate):
  1. Ensure DEBUG is False in production by reading from an environment variable and defaulting to False.

  2. Add configuration checks/deploy-time enforcement so that a deployment pipeline fails if DEBUG=True in non-development environments.
  3. After rotating secrets (CRIT-001), check logs and any leaked tokens that may have been exposed in stack traces.

### HIGH-004: JWT signing uses SECRET_KEY (symmetric key) and the secret is exposed in repository
- Files / lines:
  - /Users/admin/Desktop/intern/gdp/merental-be-3/src/application/use_cases/user/login_user.py line 89 (token = jwt.encode(payload, settings.SECRET_KEY, algorithm=algorithm))
  - /Users/admin/Desktop/intern/gdp/merental-be-3/merentalbe3/settings.py lines 131-133 (JWT_ALGORITHM = "HS256", JWT_EXPIRATION_HOURS = 24)
  - /Users/admin/Desktop/intern/gdp/merental-be-3/.env lines 1 (SECRET_KEY=...)
- Why high: Because SECRET_KEY is present in repository (CRIT-001), an attacker can sign arbitrary JWT tokens (HS256) and impersonate any user.
- Remediation:
  1. Rotate SECRET_KEY immediately (as part of CRIT-001 remediation).
  2. Consider using an asymmetric signing algorithm (RS256) with private key kept in a secure store for signing and public key for verification if multiple services need to verify tokens without sharing a secret. If continuing with HS256, ensure SECRET_KEY is strong and not shared.
  3. Add server-side token revocation or short-lived tokens + refresh tokens to reduce impact of key compromise.
  4. Add unit/integration tests that verify token verification fails with wrong keys.

### MED-006: Local in-memory cache used for rate limiting (CACHES set to LocMemCache)
- Files / lines:
  - /Users/admin/Desktop/intern/gdp/merental-be-3/merentalbe3/settings.py lines 123-129 (CACHES config using django.core.cache.backends.locmem.LocMemCache)
  - Rate-limiting decorators applied in /Users/admin/Desktop/intern/gdp/merental-be-3/src/api/users.py lines 21 and 45 (@ratelimit(key="ip", rate="5/m", method="POST") and @ratelimit(...))
- Risk: LocMemCache does not share state across multiple processes or hosts. In multi-worker or multi-host deployments, the rate limits can be bypassed since each worker maintains its own counters.
- Remediation:
  1. Use a centralized cache (Redis or Memcached) for CACHES in production so rate-limiting counters are shared across workers.
  2. Add monitoring/alerts for ratelimit bypass or sudden spikes in auth attempts.
